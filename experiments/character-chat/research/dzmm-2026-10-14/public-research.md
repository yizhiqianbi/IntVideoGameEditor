# DZMM AI 与提示词工程：公开证据调研

调研日期：2026-10-14，Asia/Shanghai。任务是学习能迁移到本人直接聊天陪伴产品的做法，不是复制平台或提取私有角色卡。本次未登录、注册、聊天、购买、创建 Bot、调用生成接口，也未读取凭证。

## 结论与证据边界

DZMM 最值得学习的是把“角色设定、可复用预设、按需背景知识、模型选择、结构化状态与应用提交”拆开。只把“可爱、温柔、像真人”堆进一条长 prompt，无法稳定决定称呼、关系分寸、记忆来源、剧情更新和主动开口。对于我们的 chat-only 原型，应该迁移这种拆分，保留本人直接讲话的输出规则；剧情旁白、动作描写和游戏选项不适合照搬。

这是一条设计结论，而不是关于 DZMM 私有服务端的断言。证据分成以下几种：

## 主聊天产品：角色与预设怎么拆

以下是既有公开 UI 快照的观察，不是本次重新打开编辑器后的结论。快照来源为 Lumivale，记录时间 2026-10-02T17:37:12.867Z（上海时间 2026-10-03）；本次[线路索引](https://dzmm-home.github.io/dzmm-addr/)同时列出 Lumivale 国内入口与 www.dzmm.ai 海外地址，补上访问线路关联。

专业模式把核心身份、开场对话、世界书、声优与发布分开；核心身份里进一步区分角色卡介绍、性格、场景、系统指令、详细描述、建议回复与推荐模型。介绍字段明确是给用户看的内容，AI 不会看到；性格字段描述说话方式与行为习惯；系统指令指导角色表现。开场允许多组对话随机选择。推荐模型只规定新聊天默认选择，玩家仍可切换。来源是本仓库 [旧快照](/Users/pencil/Documents/IntVideoGameEditor/output/dzmm/source-feature-exploration-2026-10-03.json)，定位 `type=professional-role-editor`、`character-creation-form`。

这说明至少在创作界面，“展示简介”和“实际角色演绎配置”是两种用途。它没有暴露实际服务端 messages 数组，因此不能进一步断言系统消息的顺序、某个字段一定每轮注入，或系统指令具有哪个供应商 API 的权限级别。

旧预设编辑器有两种类型：世界书条目可通过关键词触发或常驻；Apex 预设用于替换 Apex 模型默认内容指南。可确认 UI 存在这两类作用，不能据此把 Apex 当成某个已知底模、推断微调权重，或把“关键词触发”称作向量 RAG。主聊天的扫描窗口、词条优先级、截断策略、召回算法与最终拼装仍是缺口。来源：同一快照 `type=preset-editor`。

旧 UI 还提供状态栏、关系面板、背包、剧情选项和自定义面板，并称模型每轮更新。对我们的启发是把可见台词与应用状态更新分开；不能照搬“模型说关系升级就升级”。我们的后台关系阶段应保持权威，模型可表达情绪，应用决定哪些更新成立。

## 模型：能说与不能说

公开创作者经常用 MAX、XL 等产品档位称呼模型，这种名字只说明产品选项；`nalang-*` 也可能是服务别名。本次官方 Gamefy 模型目录合同区分 `internalName` 与 `displayName`，模型家族还有 `thinkingSupported`、`isApex`、会员条件和上下文变体 `maxContext` 等字段。它公开了能力与定价菜单的结构，没有公开底模映射、训练数据、训练配方或权重，不能据此认定为某个具体开源/闭源模型，更不能把“自研”的程度写成已证实。[模型列表](https://www.dzmm.ai/gamefy/docs/sdk/models.md)

搜索会出现 dzmm.app、dzmm.one、aidzmm.com 等自称官方的站点；本次没有取得 www.dzmm.ai 对它们的关联链接，不采用其中的“自研模型”“百万级记忆”“首字 200 ms”等营销说法。GitHub 同名用户、同名本地跑团项目也不等于平台的官方开源代码。

因此，这次调研不能支撑把我们现有 Grok 4.6 / low 换成“DZMM 底模”。更有价值的验证是：对同一角色、同一阶段、同一历史、同一输出约束比较候选模型，记录实际选择、延迟、格式错误、语气、重复与关系越界。

## 创作者 Gamefy：AI 调用与提示词的工程边界

| 本次官方原文规则 | 可迁移的工程思路 | 适用限制 |
|---|---|---|
| `dzmm.completions()` 只接受 user/assistant；文本来自累计内容回调，返回 Promise<void> | 为不同供应商/平台建立适配器，不能把累计文本当增量相加 | 这是 Gamefy SDK；不能说 DZMM 主聊天后端不接受 system，也不能改掉我们自己的 system 支持 |
| `default` 使用当前 chat 模型设置；目录 displayName 展示、internalName 调用 | 用户选择与目录默认值分开；调用记录保存稳定标识 | 无法由名字确定真实底模 |
| 防重复付费调用，递增请求标识拦截迟到响应；本地超时不等于底层取消 | 用户输入/切换会话优先；保留请求锁，旧回复不能覆盖新会话 | 已核验公开建议，没有调用服务端来验证执行效果 |
| JSON 先解析、校验与净化，失败走确定性降级，同一次动作不额外修复请求 | 台词可展示，状态更新单独校验；避免让格式修复重复计费 | “必须 JSON”的 prompt 本身不构成可靠格式保证 |
| 服务端函数不直接下发 prompt 源码，但模型仍可能复述指令；权限由确定性代码负责 | 把后台关系权限、来源验证、频控与计费留在代码 | 隐藏 prompt 不等于秘密保护，也不证明主聊天采用相同方案 |

精确原始章节入口：[AI 对话](https://www.dzmm.ai/gamefy/docs/sdk/completions.md)、[模型选择](https://www.dzmm.ai/gamefy/docs/recipes/model-picker.md)、[调用竞态](https://www.dzmm.ai/gamefy/docs/recipes/completions-safe.md)、[结构化 JSON](https://www.dzmm.ai/gamefy/docs/recipes/ai-json.md)、[服务端函数](https://www.dzmm.ai/gamefy/docs/serverless.md)。各章由本次取得的官方全文核验，网页检索工具单篇访问失败不再构成正文缺口。真正接入前仍需对目标 Host 的 SDK 版本和 capability 做检查。

### 公开契约暴露的 prompt 编排与上下文限制

官方 `ai-json` recipe 将 `instructions` 与 `userText` 作为独立业务输入组织 prompt，而不生成 `system` role；服务端例子把角色指令与玩家问题合进一条 `user` 消息。这是 Gamefy 作者的编排方式，不是证明 DZMM 平台主聊天的系统提示词。所谓服务端隐藏，只能避免源码或普通请求直接携带完整指令，不能保证模型不复述。[结构化 JSON](https://www.dzmm.ai/gamefy/docs/recipes/ai-json.md)、[服务端函数](https://www.dzmm.ai/gamefy/docs/serverless.md)

浏览器生成合同中 `messages` 至少一条，完整 JSON 请求最多 8 MiB，`maxTokens` 为 200–3000、默认 1000。8 MiB 是传输请求上限，3000 是输出上限，均不是模型的上下文长度。实际上下文能力需看模型目录的变体 `maxContext`，不能从传输大小宣称“百万记忆”。参数表没有给出温度、top-p 或频率惩罚，故不能推断平台实际采样设置。[AI 对话](https://www.dzmm.ai/gamefy/docs/sdk/completions.md)、[模型列表](https://www.dzmm.ai/gamefy/docs/sdk/models.md)

浏览器 `dzmm.completions` 的回调是累计文本；服务端一次性 `ctx.completions` 返回 `{text}`，`ctx.completions.stream` 则返回 `delta` 增量流。三个文本契约需要各自适配。函数单次最多三次 AI 调用、所有 `ctx.*` 共用桥接 RPC 上限；多次调用能力不等于必须设计多 Agent 或多轮修复，JSON recipe 反而要求一次用户动作至多一次 AI 生成。[ctx API](https://www.dzmm.ai/gamefy/docs/serverless/ctx.md)、[结构化 JSON](https://www.dzmm.ai/gamefy/docs/recipes/ai-json.md)

聊天存档只返回当前 active history；明确父消息 ID 用于分支，空 parent 在非空 Chat 中续接当前叶子。持久稳定 ID 的保证依赖 `chatStableIds` capability。这公开了“历史与分支”合同，没有公开自动摘要或长期记忆召回。作者仍需选择哪些历史/状态放进生成请求，不能把保存所有消息等同于模型记住所有消息。[聊天存档](https://www.dzmm.ai/gamefy/docs/sdk/chat.md)

Bot 文档是平台群聊 Bot 的 Webhook 与发消息合同，不是角色聊天主模型说明。不能用 Bot 的 API、Telegram 兼容路径或公开消息回调推导角色模型、用户聊天历史或提示词。本次 [Bot 接入指南](https://www.dzmm.ai/studio/bots/docs/)也未能刷新。

## 创作者的方法：只归属于具体作品

[世界书辅助生成器](https://www.dzmm.ai/character/3376434)的作者强调先生成、再放进角色使用并多次调试；工具把人物、世界观和文风等用途分开。这是一个实际值得学的流程：用演绎结果检验设定，不能把首次生成的长角色卡视作成品。

[避难所生存指南](https://www.dzmm.ai/character/2814538?source=home_highest_rated_7d)的创作者介绍短期对话与关键事件长期摘要，并为不同角色分别保存记忆。这只是一张游戏卡的作者声明，尚未看到代码或实测；它不能证明平台全局记忆都是该算法。

[地下城探险](https://www.dzmm.ai/character/2849651)的作者把早期固定规则与后续 AI 生成拆开，并介绍规则修改和玩家测试。它提示我们：不能用大量“必须如此”的文字代替验证；角色声音与状态一致性都要用具体场景检查。

[dzmm-builder](https://github.com/waylon256yhw/dzmm-builder)是创作者自己的公开项目，并非平台官方仓库；其自述示例采用模块化提示与状态管理，开发指南也明确声明是逆向分析。可以读作者代码来学习模块组织，但其模型表、参数限制和 user/assistant-only 说法不应单独当作现行平台事实。此次没有安装或执行其 skill、示例、登录脚本或导出脚本。

## 迁移到我们的 chat-only 原型

建议的编排如下，这是本项目设计提案，不是声称恢复了 DZMM 的私有 prompt：

```text
稳定角色身份与表达特征
+ 本人直接聊天输出契约
+ 后台当前关系与称呼约束
+ 相关世界知识 / 用户明确记忆（按来源与相关性选取）
+ 当前真实历史（作者示例另隔离）
+ 本轮用户要求与当前角色自身事项
→ 一次模型生成：实际台词 + 有限状态提议
→ 验证结构、来源、关系权限、重复和版本
→ 仅提交合格状态；仅展示实际台词
```

具体优先级：

1. **定义人的反应，而不是堆形容词。**把“软、可爱”拆成被夸、被冷落、对方疲惫、没听懂、想分享小事、需要安静等情境下的反应倾向。不要把每个情境都写成固定句；示例演示判断与语气，不成为当前历史事实。
2. **关系阶段与即时温柔分开。**初识仍可关心，亲密阶段可增加自然称呼和自我暴露；身份、重大承诺和共同经历不能随一句撒娇自动生效。
3. **世界书用于相关背景，常驻规则只放少量行为约束。**本人聊天格式、后台阶段和事实来源适合常驻；职业知识、过往事件、具体兴趣适合按当前话题注入。闭题后不继续召回该物件。
4. **让历史保留会影响下一句的变化。**偏好、已发生事件、未完成事项与承诺区别记录。摘要带来源，不能把假设、作者示例或角色想象变成用户事实。
5. **主动性保留独立决策。**角色自己的事项有进展才提供开口机会；是否联系另看用户忙碌、输入、告别、频控。Gamefy 文档没有证据证明 DZMM 主聊天具备 FlexiChrono 那类离线生活调度，不能由游戏状态面板推导主动后台。
6. **用小型对话评测修提示。**每次版本比较同一组中性场景：一句话要求、只陪不问、夸奖、拒绝旧话题、称呼偏好、关系越界试探、二十轮后回忆、主动消息被输入打断。检查第三人称/动作括号、连续追问、泛安慰、重复开头、偷造经历与阶段越界；“可爱度”需要人评，不能只用正则通过率宣告达成。

当前原型已把作者示例与真实历史分开、按相关性选记忆、后台维护阶段、结构化台词/生活提议及原子提交。后续最值得验证的是声音示例的情境覆盖、相似开头与相似内容、长对话状态恢复；这份调研没有修改角色 prompt，也没有宣称我们已得到 DZMM 私有提示词。

## 仍未解决的缺口

已经取得现行公开 Gamefy 原文。仍没有得到主聊天的完整实际请求、正式模型卡/底模映射、世界书注入次序/扫描深度/优先级、长期记忆生成与召回方法、温度与采样参数、偏好学习/微调训练或离线主动调度。需要后续正常访问公开帮助与编辑器、或在用户明确授权的测试会话里记录少量中性输入和响应，才能继续缩小这些缺口。即使取得聊天请求，也应区分“客户端传什么”与“服务端最终给模型什么”。
