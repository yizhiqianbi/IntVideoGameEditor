# 角色聊天的活人感：论文与技术报告调查

调研日期：2026-10-11。这里覆盖角色训练、角色推理、主动聊天、长期记忆、体验评测五条路线。已打开下列论文正文/作者报告及所列官方仓库；没有读取原型的用户存档，没有调用付费模型。论文效果与本项目的工程推断分开写。这里的“可爱”指用户希望的柔软、亲近、有自己的小情绪和聊天意愿，不能直接等同于任一学术 benchmark 分数。

## 能直接指导这轮实现的结论

1. **先让角色有明确的当下意愿，再让她说话。** 一串“温柔、可爱、自然”的形容词不能指定此刻的行为。每次生成应选择一个短的行为意图，例如接住亲昵、延续小梗、表达小愿望、分享角色自己的小发现；把角色的情绪原因和正在延续的事放进上下文。这个方案借鉴角色认知与规划研究，但不等于复现训练论文。
2. **把主动聊天做成可撤销的意图。** “有机会重新决定”与“到点必发旧句子”是两个机制。当前页面空闲时，可以重新决定说什么；新的输入、去忙、话题关闭、未答问题都应改变决定。无需照搬长期自主监控，也无需建立 Codex 定时任务。
3. **分条输出有用，但内容需要递进。** 第一条小反应，第二条自己的念头，偶尔第三条轻轻续一句，比把一句完整的话任意切三段更接近手机聊天。这是产品假设，仍需真实聊天比较验证。
4. **记住互动事件，不能只记个人资料。** 用户偏好是事实记忆；共同出现过的小梗、一次撒娇如何被回应，是对话事件。事件需要原文引用、说话者、时间和状态，不能由模型凭空补成共同经历。
5. **保留低推理档，不把更多推理当成可爱开关。** 2025/2026 角色推理研究支持角色定向的认知约束，但也显示知识、记忆的进步不一定带来更高的自然感/参与感。
6. **用原始多轮 A/B 证明变化。** 程序测试证明接口、取消和存档正确；不能证明可爱。保留同场景旧版/新版聊天、主动成功与失败样本，记录用户是否愿意接话，而不编造“可爱度 95 分”。

## 1. Character.AI：Inside Kaiju（2025-11-07，作者技术报告）

**问题与机制。** Character.AI 把高参与度自然聊天与通用 benchmark 优化明确区分。报告说明使用按目标调整配比的预训练数据，后训练包含 SFT、基于用户 swipe/反馈的 modified online DPO，并有分类器参与解码。模型架构的 MQA、窗口注意力、KV 共享、int8 主要解决服务效率。[官方报告](https://blog.character.ai/inside-kaiju-building-conversational-models-at-scale/)

**证据与局限。** 这是实际生产团队的一手说明，能确认其聊天能力不只来自一段 prompt；没有公开足以复现“参与感”的完整数据配方、奖励目标或对应消融，不能据此推断 Nari/Yume 使用相同模型或训练流程。

**对原型的推断。** 现在可以复用的是“优化真实聊天偏好”的目标：保存用户喜欢/不喜欢的具体回复对，写符合目标口吻的对话示范。模型架构优化不能通过 prompt 获得；DPO 必须有可训练权重和偏好数据。接入 Grok API 时只能改上下文与系统行为，不能声称获得 Kaiju 的后训练效果。

## 2. RoleLLM / RoleBench（2023，ICLR 2024）

**问题与机制。** 把角色知识与说话风格拆开：Context-Instruct 从角色资料构造知识问答，RoleGPT 以对话方式示范口吻，再用角色条件指令微调。论文比较了纯指令、few-shot prompt、few-shot dialogue；其 GPT 评测更偏好对话示范，角色资料检索也可能引入噪声。[论文正文，方法与消融](https://arxiv.org/html/2310.00746v3)

**开源实际。** 官方仓库公开 RoleBench 数据入口、方法和实验说明；README 并不是可直接启动的完整现代聊天服务，不能把“有仓库”写成模型、训练、推理全部开箱可复现。[官方仓库 README](https://raw.githubusercontent.com/InteractiveNLP-Team/RoleLLM-public/main/README.md)

**证据与局限。** 优势主要是角色知识和风格，评判模型也是数据生成者的一部分；影视/名人问答与柔软的中文伴侣闲聊不同。训练旧模型的结果不能直接外推到当前 Grok。

**对原型的推断。** 与其把可爱拆成十几条禁令，更应提供原创多轮例子：被夸后如何小得意、想陪伴时怎么说、用户短答后如何自带一个小念头。示例应明确属于作者示范，避免误作真实聊天记忆。Prompt 能调用已有风格能力，不能替代知识注入的权重训练。

## 3. Character-LLM（EMNLP 2023）

**问题与机制。** 从人物资料提取场景，补成包含经历、情绪、互动的训练数据，再训练人物模型；另构造 protective experiences，让角色遇到不属于自己知识范围的问题时保持身份边界。论文用单轮/多轮访谈检查角色记忆与一致性。[论文正文](https://arxiv.org/html/2310.10158v1)

**开源实际。** 作者提供九个角色的数据/权重差分、生成数据和 FastChat 训练入口；推理示例仍包含地点、状态和互动起点的 meta prompt。README 的“无需额外 prompt”与示例应分别理解为知识已经训练进去和仍需场景包装，而非完全无条件生成。[官方仓库](https://raw.githubusercontent.com/choosewhatulike/trainable-agents/main/README.md)

**证据与局限。** 历史人物访谈不是长期陪伴体验测试。仓库的资源限制和旧基座也不适合直接拿来作为商业聊天产品默认模型。

**对原型的推断。** 给原创角色写少量有因果的生活片段，会比“她很可爱”更可执行；例如同一件小事经历开始、进展、完成，影响下一次主动话题。它们属于虚构角色设定，必须与用户共同经历区分。只把片段放进 prompt 不是论文里的 experience upload。

## 4. Thinking in Character / Role-Aware Reasoning（2025-06）

**问题与机制。** 通用推理可能让角色只顾解题、忘掉身份，或变成正式分析腔。RIA 用情绪、经历、立场、动机约束推理；RSO 通过场景匹配的正负思考样本与偏好优化对齐风格。正文使用 Llama-3-8B、LoRA 与量化训练，也比较强行延长思考的 MoreThink。[论文方法、结果与附录](https://arxiv.org/html/2506.01748v1)

**证据与局限。** 消融支持角色定向机制，MoreThink 在一些维度退步；但这是训练后的模型实验，不能推导“所有聊天都应该关闭推理”，也没有检验我们的具体中文可爱偏好。

**对原型的推断。** 每轮保留短的结构化创作状态：我此刻是什么情绪、为什么、想怎样靠近、延续哪件事；正文只输出角色消息。无需展示长篇内部独白，也不必为了这种状态另开高推理模型。Prompt 是推理时近似，不能声称复现 RSO。

## 5. Character-R1（2026-01-08，预印本）

**问题与机制。** 将角色认知聚焦变成带标签的任务，使用维度/属性匹配奖励、参考回复重合奖励，并按角色与奖励类型归一化，做 RLVR。机制比单纯要求“多想一会儿”更具体。[论文正文，3.2–3.4 与结果表](https://arxiv.org/html/2601.04611v1)

**证据与局限。** 原表里 Qwen2.5-7B 的知识/记忆提高，但 Human-likeness 和 Engagement 并没有超过未微调基座。标签匹配和 BLEU 是可计算的训练信号，不等于内在情绪真实或可爱得到客观验证。论文指向的官方仓库 README 此次没有返回可读内容，不把模型完整发布情况写成已确认。

**对原型的推断。** 可采用“当前最相关的 1–2 个角色维度”，避免每轮注入整张巨大人设表。不能以知识平均分上升为理由换模型；用户要的是互动口吻和主动意愿。真正复现 RLVR 需要训练与奖励程序，改 prompt 只能借鉴条件化设计。

## 6. CPO / CharacterArena（2025-08）

**问题与机制。** 角色回复没有唯一正确答案，单条绝对评分容易聚在同一档。CPO 对同组候选做比较后形成奖励；CharacterArena 用共享场景的多轮轨迹进行相对评判。[论文方法与人类评测](https://arxiv.org/html/2508.09074v1)

**证据与局限。** 论文报告比较评分更接近人类判断，也承认人类评审存在明显分歧。训练目标主要仍在单轮，轨迹评测不等于训练已经学会完整长期关系策略。评审模型的偏好不能替代这个用户的偏好。

**对原型的推断。** 先用固定场景跑旧版/新版多轮，随机呈现顺序，再看“哪段更想继续聊、哪句更机械、哪里该主动”。这是现在即可复用的评测方法。若将来有足够的人工偏好对，再考虑 DPO/CPO；当前不要用一组自评数字宣布“足够可爱”。

## 7. CharacterBench / CharacterJudge（AAAI 2025）

**问题与机制。** 将人物定制拆为记忆、知识、身份、情绪、道德、可信度，区分并非每轮显现的稀疏属性与每轮可评的自然感。它单列 Human-likeness 与 Engagement，不把人物事实答对视为自然聊天。[论文框架、标注与数据](https://arxiv.org/html/2412.11912v1)

**开源实际。** 官方 README 描述先生成回复、再构造 CharacterJudge 输入；中文处理脚本确实把人设、已有对话与最后回复拼成评测对象。[官方 README](https://raw.githubusercontent.com/thu-coai/CharacterBench/main/README.md)、[中文构造脚本](https://raw.githubusercontent.com/thu-coai/CharacterBench/main/construct_prompts/process_wo_context_zh_all.py)

**证据与局限。** 基准有人工标注与专用评审，但依赖其人物、问题和标注口径。采用其“自然感”名字不代表获得同一测量，也不能给本原型伪报成绩。

**对原型的推断。** 分开检查“不会乱记用户”“能保持角色”与“说话有趣、想继续聊”。把测试场景覆盖称呼、撒娇、被夸、用户没话题、短答、去忙等，不要求每个自然回复都再陈述背景资料。

## 8. Proactive Agent / ProactiveBench（ICLR 2025）

**问题与机制。** 输入活动、事件、环境状态，模型预测用户可能需要的任务或不行动；用环境生成、用户模拟与奖励模型建立训练/评测。论文明确区分错过需求、正确安静、正确主动、错误主动；通用模型容易把不必要的帮助也判作有用，奖励反馈又可能使它过度安静。[论文正文，方法与分析](https://arxiv.org/html/2410.12361v3)

**开源实际。** 作者发布数据生成与评测入口、主动模型及奖励模型链接。README 的奖励模型集成步骤仍标记待更新，因而“已发布权重”与“集成流程完善”需要分开。[官方 README](https://raw.githubusercontent.com/thunlp/ProactiveAgent/main/README.md)

**证据与局限。** 重点是任务帮助，现实测试规模有限，主要主动结果由奖励模型评判。其错误主动率不能直接作为伴侣闲聊指标。

**对原型的推断。** 先用界面/状态规则排除不该说的时刻，再让模型从几种具体聊天意图选内容。闲聊明确开放时，候选可含延续当前梗、自己的小愿望、新的小话头；仅给“没话就输出 []”可能把模型推成永久沉默。需同时记录该说却没说和不该说却说。

## 9. PARE：Proactive Agent Research Environment（2026-04，预印本）

**问题与机制。** 静态样本无法表示主动建议如何改变用户行为。PARE 用状态机模拟用户在应用中导航，主动助手具有另一套 API 行动接口，分 observe 与 execute；评测覆盖提议时机、接受和最终目标结果。[论文全文，框架与实验](https://arxiv.org/html/2604.00842v1)

**证据与局限。** 这是状态化多应用任务环境，以模拟用户为主；并未证明哪种角色措辞可爱。论文也分析“用户尚需搜集上下文”的第三种回应，说明一次提议没被接受不一定就是内容差。

**对原型的推断。** 浏览器测试应包含动态轨迹：角色准备补话→用户开始输入→取消→用户发送→新回复；以及去忙、切会话、关主动开关。只对一个 API 响应打分，无法确认主动功能在实际使用时存在或不打断用户。

## 10. Towards Human-centered Proactive Conversational Agents（SIGIR 2024）

**问题与机制。** 该观点/设计论文把主动性分成 Intelligence、Adaptivity、Civility；具体包括多样的主动动作、时机敏感、耐心、情绪理解、尊重边界。它指出频繁澄清问题并不能自然等同于高质量主动对话。[作者公开全文](https://liziliao.github.io/papers/SIGIR24_HPC.pdf)

**证据与局限。** 它主要提供分类与设计议程，不是某个可爱角色的训练配方或因果效果实验。

**对原型的推断。** “主动”应允许分享、自我修正、说小愿望、接梗，而不是每条末尾提问；节奏可因聊天开放度调整。可爱的小不服气可以针对角色自己的小事，不应从用户短暂不回复推断“你不爱我了”。这些是产品设计选择，需要用户体验反馈来校准。

## 11. Generative Agents（UIST 2023）

**问题与机制。** 记录观察为记忆流，通过相关性、近因性、重要性检索，生成更高层反思与计划，再决定行为；消融表明记忆、反思、规划都影响模拟可信度。[论文系统与消融](https://arxiv.org/html/2304.03442v2)

**代码实际。** `new_retrieve` 对事件和想法取节点，计算三类分数再排序。公开代码的系数和近因计算与论文表述有差异：代码存在额外的 `[0.5,3,2]` 权重，近因使用排序位置衰减；不能把论文的时间衰减公式当成仓库原样实现。[官方检索模块](https://raw.githubusercontent.com/joonspk-research/generative_agents/main/reverie/backend_server/persona/cognitive_modules/retrieve.py)

**证据与局限。** 小镇模拟可信度不是亲密聊天评价，完整系统多次调用成本高；自动反思也可能把推测变成事实。

**对原型的推断。** 只借轻量形状：角色有未完的小事、最近心情原因、想分享的东西，而不是等待用户下任务。把“发生过的对话”与“角色对此的暂时理解”分层，暂时理解不得覆盖用户原话。无需移植完整城市模拟与每日大规划。

## 12. LongMemEval（ICLR 2025）

**问题与机制。** 评估信息抽取、跨会话推理、时间推理、知识更新、知道不知道。拆出 indexing→retrieval→reading；实验支持以对话轮保存内容，用事实扩充检索键，再按时间范围约束查询。纯事实压缩会丢信息。[论文正文，设计与消融](https://arxiv.org/html/2410.10813v2)

**证据与局限。** 这是长期问答准确性基准，不能保证记住资料后会自然用起来；时间查询扩展还依赖模型能准确解释时间。

**对原型的推断。** 用 shared turn 的原始片段做事件 value，用概念/人物/小梗做索引 key；保留来源 id 和日期。更新要有取代关系，回忆未知的事要能承认没记住。低成本首版可用词匹配与片段预算，不能宣称达到论文里的 dense retrieval 效果。

## 13. LoCoMo：Evaluating Very Long-Term Conversational Memory（2024）

**问题与机制。** 从人设和有日期、因果关系的事件图生成长对话，经人工核验/编辑后做问答、事件总结、图像对话评价；目的是检查跨会话时间、因果和说话者归属。[论文方法与限制](https://arxiv.org/html/2402.17753v1)

**证据与局限。** 对话是人机混合生成，不能把其平均表现当真实用户长期亲密关系质量。长上下文/RAG有帮助，仍存在归错说话者和因果理解失败。

**对原型的推断。** 角色的小生活可以有一个连续事件链：准备某件事→遇到一点小挫折→自己解决→回来分享。这些是原创虚构角色事件；“用户说过的经历”必须另存来源。测试至少要含“是她喜欢这个，不是我喜欢这个”，避免把自己的人设写到用户资料里。

## 14. Mem0（2025-04，作者预印本）

**问题与机制。** 从新消息对及历史上下文提取候选记忆，检索相似旧记忆，选择 ADD/UPDATE/DELETE/NOOP；图版本用实体关系与有效性处理变化。[论文架构与更新算法](https://arxiv.org/html/2504.19413v1)

**证据与局限。** 作者的 LoCoMo 成绩和 token/延迟优势依赖其具体基线、配置与评审流程；不是对任意聊天产品的普遍保证。抽取和更新也增加模型调用，错误抽取可永久污染人物资料。

**对原型的推断。** 当前保留可追溯、保守的用户事实采集更合适；复用的是记忆生命周期，而不是立刻把每句闲聊都送到新服务。互动事件可以存原文，角色临时心情短期有效，用户明确纠正时更新/失效。Prompt 无法替代持久化存储，但并不必然需要模型训练。

## 15. Proactive AI：From Turns to Replannable Dialogue Timelines（2026-10-04，预印本）

**问题与机制。** 把对话表示为连续事件时间线与可重规划消息队列。未来动作区分已准备的 Send 与到时重新决策的 Reconsider；新输入能撤回、改变或推迟尚未发出的动作，交付前重新核对最新上下文。文本明确将生成判断与确定性时钟/顺序控制分开。[论文全文，需求与形式语义](https://arxiv.org/html/2610.05159v1)

**开源与证据。** 作者提供研究原型仓库。[官方仓库](https://github.com/airalogy/proactive-ai) 本工作主要是形式语义、实现及示范；没有证明这种队列让人物更可爱，也没有完成大规模长期伴侣效果评测。刚发布的预印本不能当成成熟商业实践的保证。

**对原型的推断。** 可采用简化版：保存有来源、可失效的小接话意图；到点时读取最新 revision 再生成，输入变化就撤销，前景消息优先。暂不照搬强制打破沉默、跨日自动联系或后台长期自主循环；目前用户要的是当前聊天可爱主动，授权范围与“不设定时优化”仍有效。

## 建议的最小系统形状

以下是基于以上资料的工程提案，尚不是这些论文已经证明的最终效果。

```text
用户输入 / 当前页面空闲事件
  → 确定性门控：可见、未输入、未去忙、未关闭话题、频率预算
  → 取上下文：角色设定 + 有因果的当前小事 + 用户偏好 + 原始互动片段
  → 单次 low 生成：短行为意图 + 情绪变化 + 1–3 条有递进的消息
  → 验证格式、来源、重复与当前 revision
  → 持久化并逐条显示
  → 保存可撤销的后续意图；到时重新考虑说什么
```

无需把隐含思考全文放进界面。可采用意图枚举与简短可观察状态，例如 `share_small_joy`、`continue_shared_joke`、`seek_light_closeness`，而不是每轮要求模型解释心理分析。若行为意图只是一串固定文本或硬编码台词，同样会显得机械；应由真实上一轮关系与事件选择。

## 哪些现在能做，哪些需要训练

| 目标 | 当前 API + 工程可做 | 无法靠 prompt 等价替代 |
| --- | --- | --- |
| 可爱口吻 | 少量高质量原创多轮示范、短句与有原因的小情绪、按场景选择 | 角色风格 SFT/DPO 对权重分布的持久改变 |
| 主动性 | 页面内事件、候选意图、可撤销计划、重新判断、频率/忙碌门控 | 特定主动预测或奖励模型训练的论文效果 |
| 长期一致 | 事实与事件分层、来源、时间、取代、按需检索 | 权重内人物知识注入；完美跨会话记忆 |
| 活人感证明 | 同场景多轮对比、真实输出、用户偏好、动态 UI 测试 | 程序测试通过、模型自评、benchmark 平均分不能代替体验 |

这轮应优先做口吻示范、当前意愿、互动片段与可撤销主动机制。训练路线留在真实偏好样本足够、基座风格确实成为瓶颈时再做；现在保持 Grok low 并不妨碍验证这些系统改动。
