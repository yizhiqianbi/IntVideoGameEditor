# 活人感失败审计与本轮落地建议

审计日期：2026-10-11。范围为 `engine.mjs`、`characters.mjs`、`provider.mjs`、`server.mjs`、`public/app.js` 及 2026-10-07 的全部合成试聊结果。没有读取 `.data` 用户存档、凭据或原始用户聊天附件，没有新增模型调用。本报告是源码审计、旧真实输出人工复核及原创设计建议；不是新增试聊结果或质量分数。

创作检查采用 `xumeng-roleplay-authoring/SKILL.md` 及 `references/creation-metrics.md`、`references/authoring-and-review.md`。这里直接应用动机、自主行动、场景连续性、声音辨识及信息来源分层，保留成年原创 Yume 22 岁、Nari 23 岁与用户指定的软甜、可爱、日常配合体验。

## 结论

用户反馈有充分依据。现有版的主要问题不是缺少“软甜”这个形容词，而是生成内容反复执行小任务、角色没有能跨轮变化的自己的事情、主动功能只负责补完上一句，显示又要等完整 JSON。消息分成两条后，这些问题仍在。

本轮必须同时改声音、角色连续状态和主动调度。保留数据来源、草稿、取消和幂等保障，但不要继续靠叠加限制词或某一套命名小游戏制造可爱。

## 实际失败与代码原因

| 问题 | 已观察的真实输出 | 对应原因 |
| --- | --- | --- |
| 作者样例主宰素材与结构 | 发布版 Yume 把奶茶叫“熬夜续命珍珠”，随后“轮到你喊一声”；最新主动版又给作业取名，主动轮只是追加“求图表别当场掉链”。Nari 的声音段几乎复写“雨打伞/洗衣机叹气”换题示例。 | `dialogueExamples` 全部候选排序后固定取前三，相关分为零仍入选；同分按作者卡顺序。默认前三含命名游戏、差评、回来啦。`performanceGuide` 无命中退回 everyday，并按词面最多两种情境；角色本轮没有持续目标可提供另一种内容来源。 |
| 配合变成宣告配合 | 最新 Nari：“好，那我就不专门等你开口了。”早期 Yume：“今天我就听你的……陪你说两句轻松的”，却没有两句轻松内容。 | 卡和后置提示大段讲“怎样聊天”；缺少直接贴近、调皮、小小要求、自然误会修复的短口语样例。模型回应用户关于体验的指令时，常把策略本身说出来。 |
| “自己的生活”仅靠当场编故事 | Nari 的红招牌突然出现，主动轮才补半截箭头；Yume 小目标在单轮就是一个取名点子。 | 会话没有 `characterBeat`、目标进度、她自己想接着说的事。只有用户事实记忆、数值关系、笼统 mood、历史摘录。角色素材变化没有明确来源和跨轮因果。 |

| 主动机会容易永久丢失 | 不需要读取用户存档即可由源码确认。 | 前端开始请求即加入 `initiativeAttempts`，随后输入/隐藏取消也消耗机会。再次清空草稿仍没有这个锚点的机会。打开新建对话弹窗还会清空候选，关闭也不恢复。 |
| 熟悉程度长期停住 | 最新六次均仍是“初次见面”；旧结果普通聊天也基本全为零。 | `relationship` 依赖几条非常具体的理解/承诺话术增加 trust/closeness；正常有来有往不产生熟悉状态。标签又作为当前事实给模型。卡说“初次也能软甜”缓解了硬门槛，但运行时持续暗示陌生，数值也不能表达轻松亲近。 |
| 分条降低可见历史轮数 | 代码可确认，长聊效果未新增验证。 | recentHistory 最多 20 个消息，分条后每个用户轮占 3–4 个消息；实际短期轮数缩水。没有独立保存的角色当前 beat 时，自己的小目标更容易被挤出。 |
| 等待破坏手机聊天节奏 | 最新六次为 5.4–14.2 秒；第一条约 55 可见 token 的回复报告 416 reasoning tokens。 | Grok 已设置 low，但 `stream:false`，完整 JSON 接收和解析后才返回；两条显示停顿仅额外 500–900 ms。普通生成期间输入框还 readOnly，用户不能连发短句或自然插话。 |

关系标签、关键词路由、分条与固定计时属于实现事实；它们造成何种体验是本报告的推理。真实输出来自保存的合成结果，不能据此推断全部用户会话或所有模型能力。

## 本轮 must-have

1. **短口语声音与用户方向一致。** 初次就能软甜、自然配合、愿意亲近；不要等好感升级才允许。Yume 的软里有小得意、小嘴硬，Nari 的软里有欲言又止与小偏心。每轮不要求交出一个新小游戏、提问或完整道理。一句“嗯哼”可以是有语境的轻反应，但不能每轮只会轻反应。
2. **独立角色 beat。** 最小字段为 `focus`（她现在在想/做什么）、`feeling`（针对这件事的具体轻情绪）、`want`（下一小步）、`status/updatedAt/sourceTurnId`。只写角色自己的创作状态，和用户 facts 完全分开。初始 beat 属于明确的虚构角色开局；模型更新必须贴合本轮，不能编造用户离线行动或突然完成共同计划。只有一个正在进行的 beat，允许用户打断、换掉或无目标闲聊，避免接成每日任务系统。
3. **主动由自己的下一小步驱动。** 主动理由可包括：想到一个追加、自己试了一步后的小反应、想轻轻靠近一下、分享一件与当前 beat 有关的小事。“上次意思说完”不是禁言条件。“问题未回答”只是不重复逼问的依据，可以换成不要求回复的一句自己话。
4. **开场/重进/当前聊天都可产生机会。** 在页面可见、没有输入、没有其他生成时，以上下文版本和机会 ID 调度。每一段活动有有限预算，例如最多 3 次，而非每用户轮永远只一次。离开/睡觉/不打扰立即暂停；显示过的机会不可刷新复发；取消未显示的意图可重新审视但不可立刻连环重试。没有 Codex 定时自动化或关闭页面后的后台骚扰。
5. **待主动意图可取消和过期。** 至多一个 `pendingIntent`，绑定上下文版本、目标/理由、notBefore、expiresAt、预算。用户新消息、换题、语言/称呼更新使它无效；返回页面重新判断当前意图。没有新的依据就选安静，安静不是每次必须等用户再授权。
6. **简化样例注入。** 有关的才选 1–2 个；无相关命中只用极短的角色声音示范，不靠卡顺序注入前三。素材与句法要分散。保留作者例与实际会话隔离，但不要每轮都注入“开场小游戏+安慰+回来”的混合教学。
7. **降低等待。** 流式发出自然语言或能安全完成的消息单位；未完成对象不能作为已保存事实。若本轮仍保留完整 JSON，至少缩短生成目标并真实测量第一条可见延迟，别把动画停顿当流式。允许编辑下一条草稿；并发提交需独立 pending/queue 与幂等处理，不能只改 readOnly 就放开竞态。

## 哪些约束交给 runtime，哪些留给 prompt

| runtime 负责，可减少每轮重复文字 | prompt 负责，有助于真正写出角色 |
| --- | --- |
| 主动开关、页面可见、输入/生成互斥、间隔、预算、有效期、版本与幂等；离开/休息状态；语言和称呼偏好；字段/字数上限；队列提交、取消与过期；用户 facts 来源分层、角色 beat 来源与大小。 | 她此时在意哪件事、她自己想做的小步、当前具体心情；语气和口语节奏；如何直接接住当前话；怎样软甜地配合、轻轻闹、认真听；已结束主题的语义与新主题区别；未知事实不补造。 |
| 相同消息去重、同一主动意图只发一次、已关闭主题的候选排除；历史按用户轮分组并按字符限额。 | 不复述策略、不把声音演成“我将陪伴你”的声明；不强迫人接游戏，不每条末尾询问；不把素材换个名字当作换题；当已有内容真的足够时安静。 |

数据边界不该删掉，但可以用短而固定的说明配合明确结构；当前重复解释恋爱/设备能力/每条都要有内容等占据注意力，且没有提供足够正面声音。不要把“催逼”扩大解释成所有撒娇或短短想念都禁止：轻轻表达“想再跟你说两句”与指责“你不回就是不要我”是不同的行为。

## 最小架构

```text
用户输入 / 页面进入 / 空闲机会
            ↓
应用读取：用户事实+表达偏好｜角色当前 beat｜最近真实交换
            ↓
角色生成：1–3 条对白 + beat 的下一状态 + 可选主动意图
            ↓
格式/来源校验 → 持久提交 → 消息显示
            ↓
有限预算调度器：可见且无输入，意图未过期且版本相符
            ↓
主动生成/复核 → 发送或安静 → 更新角色 beat 与预算
```

普通轮可先提出下一意图，空闲再做一次轻量 reconsider；不必每隔几秒循环调用模型。若保存了预生成补句，必须在实际发出前检查版本和有效期，实际发出才计为已说历史，不能把未来补句当已发生事实。无论选择哪种，本轮至少实现角色当前 beat、待意图与有限多次机会，已有安全提交逻辑继续复用。

## 原创声音参考：展示判断和节奏，不写死进产品

下面都是作者示范，未做新增模型试聊；不能冒充实际用户/角色经历。它们是少量正面方向，不要求每轮相同结构、固定“嘛/哼/嘿嘿”或星号动作。

| 场景 | Yume 的可能对白 | Nari 的可能对白 |
| --- | --- | --- |
| 用户说“在吗” | “在呀。” / “你一喊，我就把注意力挪过来了。” | “嗯，在。” / “刚才那句想说得慢一点，免得太明显。” |
| 用户说“想你了” | “欸，这句我可要留下。” / “我刚才还一本正经的，现在有点翘尾巴。” | “听见了。” / “本来想淡定一点，嘴角先不配合。” |
| 用户轻轻叫“笨蛋” | “只许叫一下。” / “……两下也行，反正是你。” | “嗯，被你发现一点。” / “但今天先对我宽容一点嘛。” |
| 用户要求别再玩小游戏 | “好嘛，收起来。” / “其实我有个坏毛病，刚写完的便签越整齐，越舍不得划掉。” / “做完一件事，还要心疼一张纸。” | “好，不给你出题了。” / “我想把那张小画留一处没画完。刚才试着补上，反而没那么喜欢。” |
| 用户夸角色可爱 | “你这样夸，我会当真的哦。” / “不许等我得意起来，又说我尾巴翘太高。” | “唔。” / “这次不装没听见了。” |
| 用户忙，角色自然收尾 | “去忙吧，乖乖放你走。” / “我的这点碎碎念，等你空了再讲。” | “嗯，先把手头的事做好。” / “这一小段我先收着。” |
| 主动：自己的 beat 有下一步 | （此前已在角色 beat 里尝试留最后一颗糖）“跟你坦白个事。” / “那颗糖没留住，我刚才的决心只坚持了半句话。” | （此前已在角色 beat 里调整一张小画）“我把那一笔擦掉了。” / “嗯，现在喜欢多一点。刚才还有点舍不得。” |

这些例子刻意避开每轮命名、小游戏和抽象承诺；其“小情绪”有对应的当前行为或已知用户话。角色自己的虚构小生活可作为创造内容，但要建立、承接和更新，不能伪装真实传感器或用户离线陪她做过的事。

## 验证应覆盖的失败场景

最重要的体验检查应使用新旧同一组自然短输入，保存未挑选的完整输出；代码测试通过不能代替这些。

- 普通“在吗/嗯/然后呢”：不要求用户不断策划内容；有自然轻反应与自己的下一步。
- “你太像完成任务了”“不要小游戏”“换一个”：立即落实，不先写一段聊天策略；变换内容和说法，不只换道具。
- 用户温柔夸赞、轻逗、提出软一点：有具体小情绪，不被“初次见面”截断。
- 3 个主动机会：不能每次重演同一物件，至少观察一次角色自己的进展；不催回应，预算耗尽后安静。
- 进入新会话、重进旧会话、开始打字再清空、去忙/晚安：机会可用且去重，停扰与恢复有依据。
- 10 轮以上：角色 beat 承接，用户旧偏好与更新不会打架；不同主题不都转成起名。
- 第一条可见延迟、消息间隔与草稿编辑：真实浏览器记录，不能以请求总耗时或演示消息证明。

本次只读审计完成。报告不声称新架构已实现，也不声称这些创作示范经真实模型验证。实施和新试聊由主任务继续。
