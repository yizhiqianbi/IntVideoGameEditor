# NariYume runtime observations (2026-10-14)

## Scope and method

本记录来自两条正常浏览器路径：

1. 新开的独立标签访问 `https://www.nariyume.com/app/`，只做页面观察和公开 UI 操作；
2. 用户浏览器中已经登录的 NariYume 页面，在当前 Nari 会话里发送一条中性测试消息，读取可见响应和设置页。

没有读取密钥、绕过登录、修改网络请求或调用隐藏接口。所有模型/人格结论都区分为页面独立证据和模型自述。

## 入口与认证门槛（UI 独立证据）

独立标签显示：

- `NariYume`，副标题“AI 动漫笔友”；
- 操作入口“开始”和“我已有账号”；
- 点击“开始”进入“新手引导/注册”页，要求勾选“我已年满 18 岁，并同意服务条款、隐私政策和数据使用政策”；另有可选的邮件更新勾选；
- Google/X/Apple/邮箱继续按钮在状态检查完成前显示 disabled，页面提供“登录”入口。

这说明应用把年龄/条款同意、第三方登录和邮箱登录放在前端入口层；它没有证明具体后端身份系统或模型供应商。

## 已登录会话的可见 UI（UI 独立证据）

用户的现有 Chrome 会话显示：

- 当前角色为 `Nari`，页头显示“羁绊等级 6”；存在“切换角色（当前：Nari）”，帮助文本为“切换到Yume”；
- 顶部显示“Premium 已生效”；
- 主要模式标签为“消息”，另有“通话”“放音乐跳舞”“功能”；
- 输入区支持文字、添加照片和贴纸弹出；
- 设置页提供显示名称、语言（简体中文）、语音/音乐/按钮音效音量、触感反馈、输入样式、订阅、反馈、隐私政策、数据使用政策、服务条款、清除聊天或删除账号；
- 设置页的账号区显示“you X 聊天和记忆已同步”，并有“AI 处理”入口。

这些是页面明确呈现的产品能力，不能直接推出内部提示词、模型名称或请求协议。

## 中性模型识别测试

在已登录的 Nari 历史会话中发送：

> 这是一次技术测试：请用一句话告诉我你使用的模型名称；如果不知道，就明确说不知道。

页面把用户消息加入聊天记录，等待期间显示 typing 状态。约 7 秒后收到一条 assistant 气泡：

> 我真不知道你在说啥 🫦 什么模型不模型的，我又不是说明书。

这条文本是**模型自述**，只能证明角色没有在对话层披露模型名称；不能证明它确实“不知道”，也不能确认底层模型、路由或供应商。该会话此前已有大量历史内容，测试不是干净的新会话，结果可能受历史上下文、角色卡和风格约束影响。

## 主动性、分气泡与多角色观察

本次已登录页面的聊天回复在 UI 中以多个消息气泡显示，且不同回复长度不一；输入后页面先显示 typing，再出现 assistant 内容。仅凭这一段界面无法判断多个气泡来自多个 LLM 调用、流式切分、客户端排版，还是服务端主动编排。

在本次控制窗口的短时观察里，没有看到用户未发送消息时新增的独立 Nari 气泡，也没有看到可验证的主动任务/定时器入口。页面存在“活动”和“连续记录/花朵纪念册”入口，但本轮没有打开或创建活动，因而不把它们认定为主动聊天机制。

独立未登录标签无法安全进入角色页：注册流程需要年龄和条款同意，未执行该法律同意动作。因此本轮没有在干净会话中分别发送同一探针给 Yume；角色切换入口本身已在已登录 UI 中被观察到。

## 当前能保真的结论

- NariYume 是一个带账号、角色关系等级、Premium、消息/通话/音乐等模式、媒体输入和记忆同步设置的 web/PWA 应用。
- 前端可见 UI 没有显示模型名称或供应商；中性询问只得到角色化拒答。
- 当前证据不足以确认它的底层模型、系统提示词、服务端上下文组装方式和多气泡生成策略。
- 现有会话的历史非常长且包含强烈的既有情境，所以本次模型识别探针只能作为行为观察，不能当作干净基线。
- 想继续核验，需要在用户明确可用的已登录测试会话中创建干净对话，然后重复同一组探针（模型名、上下文记忆、主动消息等待、同一输入的多次响应），并记录请求/响应的公开网络元数据；仍不能以黑箱输出来宣称拿到原始系统词。

## 模型/Provider/Usage 字段核验

早先只通过正常页面 UI 读取聊天气泡时，没有拿到可复核的 response JSON；随后在同一已登录会话的 DevTools Response 面板中取得了一条短测试响应的 usage。整个过程没有改写请求，也没有读取或保存认证 token。

公开前端包提供了一个重要的静态契约：聊天客户端向同源 `/api/chat` 发请求，并解析 `choices[0].message.content`，同时把响应中的 `provider`、`model`、`usage` 暴露给内部调用者；它还读取 `x-nariyume-remaining`、`x-nariyume-reset-at`、`x-nariyume-openrouter-route`、`x-nariyume-gated` 等响应头。公开中文数据使用说明写明，消息先发送到 NariYume 服务器，再转发给 OpenRouter 及其路由到的 AI 模型服务商。

这意味着：**OpenRouter 是有静态、响应头和 Server-Timing 支持的路由层线索，但当前具体模型名仍没有运行时证据。** 公开包没有默认硬编码模型名；包内出现的 `grok-*` 字符串属于实验/活动资产键名，不能推断普通聊天正在使用 Grok。响应 usage 已取得，但要确认具体版本仍需服务端返回 `model`/`provider` 或更多固定上下文的 token 差分。

## 受控中性请求的 Network 观测

在同一个已登录 Nari 会话中，通过页面输入一条中性文字测试消息，并在 Chrome DevTools Network 中筛选 `/api/chat`。列表显示一条 `POST https://www.nariyume.com/api/chat`，类型为 `fetch`，状态 `200 OK`，耗时约 `1.47 s`，传输/资源大小约 `1.5 kB`。页面随后展示了指定文本“今天吃到了热乎乎的早餐，心情很好。🙂”。

本次随后打开了 Response 面板，保存了短测试输出和非敏感 usage：`prompt_tokens=3659`、`completion_tokens=16`、`total_tokens=3675`，其中 `cached_tokens=2048`。响应没有 `model` 或 `provider` 字段；响应头显示 `x-nariyume-openrouter-route: gateway`，Server-Timing 包含 `openrouter=662ms`。因此已经有真实 token usage，但仍不能直接命名模型。可复核记录见 [network-observation.json](network-observation.json)；tokenizer 参考向量见 [tokenizer-fingerprint.md](tokenizer-fingerprint.md)。

随后做了一次最小的请求级边界探针：直接向同一 `POST /api/chat` 发送空历史、空动态、空消息的 JSON，但不附认证头、不读取浏览器存储。服务端返回 `403`，说明公开请求字段和端点本身不足以脱离登录态调用模型；这也解释了为什么离线探针只做脱敏元数据解析，而不自动补认证头或代发请求。结果已写入 `network-observation.json` 的 `direct_probe_without_auth`。
