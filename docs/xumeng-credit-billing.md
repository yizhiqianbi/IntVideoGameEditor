## 定价与成本口径

当前收费公式：`Credit = ceil(可信模型美元费用 × 请求冻结的美元兑人民币汇率 × 3 × 100)`。¥1＝100 Credit，逐笔将最终费用向上取整，不在换汇或中间步骤提前取整。

“成本”指 OpenRouter 在服务端返回的实际模型接口费用 `usage.cost`；需要补核时使用匹配生成编号与模型的 `total_cost`。缓存、供应商和长上下文档位都会影响实际费用，不能直接用官网标准 Token 单价代替。模型思考已包含在费用里，不能再加一次。

当前政策格式 version1、价格 revision1、费用倍数3。汇率使用欧洲央行 2026-10-06 的参考数据：EUR/USD 1.1269、EUR/CNY 7.5554，换算 USD/CNY 6.704587807…，采用6位小数 **6.704588**。这只是参考汇率，不保证等于银行卡结算汇率；需要更新时修改政策，新请求使用新值，已有请求继续使用冻结值。

| 项目 | 当前配置 |
| --- | --- |
| 模型 | x-ai/grok-4.6 |
| 标准价格参考 | 输入 $2／百万 Token，输出 $6／百万 Token |
| Credit 标准价参考 | 输入4.022753／千 Token，输出12.068258／千 Token |
| 供应商请求价格上限 | 输入 $4.4／百万 Token，输出 $13.2／百万 Token |
| 实际结算 | 实际美元费用换算后 ×3，合并向上取整 |

3倍成本的收费相当于模型费用口径加价200%、毛利率约66.7%，整数 Credit 取整可能使小额请求的比例略高。这里尚未计入 OpenRouter 充值手续费、支付通道费、服务器、税费、VIP赠送额度、失败成本或退款，因此不能据此承诺最终净利率。现有 ¥28／¥88／¥188 充值包与 VIP 领取额度进入同一个钱包，模型消费使用同一套规则。

生产使用 `CREDIT_BILLING_ENABLED=true`、`CREDIT_BILLING_RATES_JSON` 和 `CREDIT_BILLING_COST_POLICY_JSON`。参考 Token 价格支持最多6位小数，真实美元费用支持最多12位小数，计算使用十进制定点与 BigInt，避免浮点误差多扣1 Credit。启用但配置非法时拒绝生成；关闭时公开接口不提供默认价格。

网页网关的价格上限必须存在且不超过请求冻结政策的上限。配置不一致时在发起模型前拒绝并释放已有预留。旧账单不带成本政策，仍按自己的冻结 Token 费率结算，不转换历史消费。

## 扣费流程

1. 网关先验证会话、请求、人设与最终提示，只读查询本人可用余额。按输入字节保守上界和最高供应商单价，选出余额可承受的回复 Token 上限，再重建实际模型请求、指纹并原子预留。预留金额是上限，不是实际消费。
2. D1 在单次事务内检查余额和已有预留。账户与请求编号唯一，重复请求不能启动第二次模型调用。
3. 生成完成后，按可信上游实际美元费用与请求创建时冻结的政策结算，释放差额；Token 用量同时保存供核对。扣费不会超过预留金额。
4. 无有效输出、无效的剧情记忆或生成前失败，释放全部预留。已交付有效文字后停止或中断，按实际用量结算。
5. 有输出但缺少有效 Token 或美元费用时等待核对；通过服务端提供方元数据补齐，超时释放预留，未确定的模型成本由站点承担。

后台每分钟先释放到期预留，再轮转核对最多 10 条待结算记录；余额视图即时忽略到期占用，即使定时任务延迟也会恢复可用金额。成本模式下，元数据必须匹配原生成编号与模型，并提供有效的实际费用和原生 Token；模型匹配只允许名称完全相同或经过官方目录独立验证的固定版本映射，不按前缀猜测。实际费用已涵盖思考，允许非零思考量。旧 Token 计价账单仍要求原生思考 Token 明确为零，不猜测用量。

剧情记忆整理是一笔独立模型请求，使用同一套成本政策、预留和失败处理。每批成功都会保存进度；后续正文失败、余额不足或取消，不会撤销前面已成功摘要的消费。原始对话仍保留。

## 聊天界面的余额与错误恢复

服务器收费开关开启后，聊天页读取 `/api/backend/v1/billing/usage` 中当前正式账户的可用 Credit、预留与欠额。关闭时余额组件不显示、不查询；游客显示登录入口，不查询本人消费。账户切换与刷新使用不同请求键，旧账户的余额不能继续显示；读取失败会清空旧结果，并提供手动重试，401／403 可重新登录。

每次实际进入生成流程后，完成、停止或失败都会触发一次余额读取。如果读到未到期的预留或 pending 记录，最多在 2 秒后补读一次；之后由用户手动刷新，不持续轮询。界面显示“待核对”，不会把预留金额当作已结算消费，也不能保证一次延后读取就完成用量恢复。

发送与重生成前先确认已读到服务端费率配置；配置未知时提示刷新，扣费开启时先要求游客登录。聊天、小说和摘要先按可用余额选择回复长度，保留全部输入；聊天/小说最低128 Token，摘要最低512 Token，明确请求更低上限时保持原值。最低上下文加回复仍不够时返回402，说明当前可用和至少所需 Credit，有其他请求预留时同时说明。实际结算仍以可信费用资料决定，差额返还。

消息菜单已经支持右键、“更多”和键盘菜单入口；“选择文字”保留原文格式，用户与助手消息可编辑。编辑不调用模型、不改变历史消费记录；清理受修改影响的摘要与世界快照，并保留后续原文。历史助手回复重新生成时建立新分支，原会话保留；末条且紧邻用户输入的助手回复沿用原会话重生成。重生成是新的模型请求，收费开启后仍计费，不复用旧回复的收费结果。具体历史处理见 [角色对话系统文档](/Users/pencil/Documents/IntVideoGameEditor/docs/xumeng-roleplay-system-architecture.md)。

## 权限与数据

`BillingService` 是 Cloudflare 命名服务入口，只有网关的 `BILLING` 绑定能调用预留、结算和维护。普通 HTTP 不提供这些写接口。浏览器不能指定收费金额、实际 Token 或结算授权。

`0015_credit_usage.sql` 新增独立请求、消费账本与余额视图；`0020_credit_cost_pricing.sql` 仅增加可空的冻结政策和美元费用两列，不改写历史 Stripe、Z-Pay、订阅或聊天记录。真实充值、已领取订阅额度与消费共同计算可用余额；Stripe 沙盒金额和未签到的订阅权益不进入可消费余额。真实退款造成的欠额单独显示，可用余额下限为零。

公开费率：`/api/backend/v1/billing/config`。本人消费记录：`/api/backend/v1/billing/usage`。充值页展示分页记录；收费开启后，聊天输入框展示服务端费率和本人余额状态。两处均不写死收费价格。

公开记录不包含结算密钥、请求内容指纹或提供方生成编号。每次调用携带独立的 `X-Xumeng-Request-Id`，只用于定位和防重复。
