# 叙梦小说创作与本轮体验

本轮按用户的手动请求，调研 DZMM 小说创作模块，并分别以 User 和 Dev 体验消息、论坛、创作。新增作品工作台入口为 https://xumengchat.top/#novels ，也可从「创作 → 小说与故事」进入。

## 来源站的真实体验

2026-10-07 通过来源站界面探索 [小说目录](https://www.dzmm.ai/novel)、私人作品列表、[创建书籍](https://www.dzmm.ai/novel/book/create)和[自动小说家](https://www.dzmm.ai/novel/ai-workspace)。来源站分小说与独立故事，书籍表单提供标题、简介、标签、封面、网址标识及作品来源。自动小说家的实际流程是：选择标签 → 编辑创作指令 → 生成可编辑的大纲（世界、人物、剧情段落）→ 开始正文创作。

这解释了它与单人角色聊天的区别：作者先控制整体设定和情节，再逐步形成成篇内容。叙梦沿用这个创作方向，另外明确了私人保存、章节顺序、失败恢复和生成预览的边界。没有复制来源站的小说正文或人物设定，也没有把其公开目录当作我们的作品。

实际体验「精细创作」会立即创建项目并触发指令生成；其后又完成一次大纲生成，合计来源站 AI 操作 2 次。界面没有显示模型、Token 或费用，不能推算为零。临时项目 b7b69291-3bf5-4434-9042-1c10399d92d7 已从来源站删除，项目数量恢复到本轮基线 0。本轮没有执行来源站正文生成、公开发布或付款。

## 叙梦这一版的产品流程

1. 登录后新建小说或独立故事，填写标题、简介、标签、创作指令和大纲。
2. 添加、重命名、删除、排序章节，编辑正文；整个作品一次保存。阅读页按当前章节顺序展示，未保存稿也能预览阅读。
3. AI 可生成大纲或续写当前章节。结果以流式文字进入预览，原稿保持原样；作者点击插入或追加后再保存。中断时保留已收到的预览，未插入的预览在导航时有保护，支持导出。
4. TXT 导入成为新作品，长文本分章且保留空白与 Unicode；JSON 备份包含完整设定和章节，导入时生成新作品、章节编号，不覆盖原作品。
5. 正文修改按账号、作品和页面分别保留本地恢复副本。多个标签页的未保存稿独立列出，可分别继续编辑、导出或放弃指定版本。保存失败、账号切换或提交结果未知时，不把错误响应当作未提交；恢复后遇到版本冲突，可导出或另存副本。

当前版本是私人创作工作台。封面上传、公开小说目录、投稿审核、公开阅读网址及自动连续多章生成尚未实现；不会把它们显示为已经可用。AI 的真实成文质量尚未通过线上模型样本验收，界面与请求链路的隔离验收不能替代这一点。

## 存储和并发

新增 D1 `novels` 与 `novel_chapters` 表，不把长篇正文塞入角色聊天 state。作品归属由服务端会话决定；请求中的 accountId 只用于确认旧标签页没有跨账号提交。不同用户的相同作品或章节编号彼此隔离。

`GET /v1/novels` 列出当前账号作品，`GET /v1/novels/:id` 读取整稿。`POST /v1/novels` 新建，`PUT /v1/novels/:id` 用 version 保存完整快照，`DELETE /v1/novels/:id` 按归属和 version 删除。写入的元数据、移除的章节、新增/改动的章节及返回快照在同一 D1 batch 事务中完成。服务端 mutation token 防止旧版本输家清理并发赢家章节；冲突返回 409 和当前快照，不强制覆盖。读取作品与章节也在同一批次中，避免跨版本拼接。

限制：整稿 JSON 1.5 MB、最多 100 章、每章 50,000 字，标题 120 字、简介 4,000 字、指令 8,000 字、大纲 20,000 字、20 个标签。超限明确拒绝，不静默截断保存或导入。恢复与导出可以保留超出保存总量的原稿；浏览器存储空间不足时会显示提示，仍可导出。

## AI 请求与计费

`POST /api/novel-generation` 接收 operation、作品资料、当前章节上下文和模型档位。续写只发送当前章末 12,000 字，以及前两章各自末 3,000 字，另带大纲、简介与指令；界面会说明这一范围。它不是全文检索或整本书长期记忆。增加长篇专用摘要前，作者应在大纲/指令中维护必要的事实。

小说有独立写作 system prompt：区分世界规则与当前情节，要求人物目标、能力限制和行动结果具备因果；近期正文优先于旧场景，不反复搬出失效物品或约定。小说作者可以安排所有虚构人物的对白和行动，因此不套用角色聊天中「不得代替用户行动」的约束。大纲操作输出世界、人物与分章因果，续写操作仅输出新增正文。Prompt 策略沿用默认创作技能的状态与因果原则，不声称模型已保证连贯性。

网关复用已有认证、来源校验、账号/IP 限流、生成请求编号、钱包预留、供应商价格上限、取消/失败处理与可信实际费用结算。思考强度仍为 low，收费政策保持实际美元成本 × 冻结汇率 × 3 × 100 Credit/元，并向上取整。无有效输出返还预留；已输出部分使用可信实际费用，缺失用量按已有待结算恢复流程处理。没有新增免费接口绕过钱包。

这版小说请求在底层生成账目中仍归 `chat` operation，与聊天共享限流；并未加入一个不受旧数据库约束支持的新计费类别。钱包分类未来若要单独列出「小说」，需一起迁移账目类别和展示。保存、阅读与导出作品不调用模型。

## 消息与论坛的实际问题

真实 TavernApp 隔离体验发现：重复选择或切换会话清空输入；请求失败将原消息写回输入框，覆盖等待期间新输入。修复后，各会话在当前页面内保存自己的输入，重生成不清理未发送文字；失败时保留新稿并提供原消息恢复入口。恢复采用追加，不静默覆盖。账号改变清理输入并中止旧请求。此输入保护是当前页面内的状态，不宣称跨刷新保存聊天输入。

真实 ForumView 隔离体验发现：回复输入跨帖子串用，旧请求成功会清空当前新文字，详情 404 没有返回入口。修复后按帖子及输入版本保存草稿，只有提交版本仍未修改时才清理；旧帖子响应不改变当前帖子状态，失败保留文字，404 仍能返回。账号更换清理草稿。独立 Dev 审查另外发现旧论坛保存回调可能绕过小说导航保护，增加当前路由检查和组件卸载失效保护。

## 第十九轮：多标签页恢复保护

2026-10-08 用两个隔离浏览器标签页、真实 NovelStudio 和原创测试稿确认了 XM-025：A 页未保存正文被 B 页另一作品的恢复记录覆盖，B 保存后删除共用账号键，A 刷新只剩旧云端正文。恢复存储现在使用 `xumeng-novel-recovery-v2:<账号>:<页面 owner>:<作品>` 独立记录，页面重新打开或复制时创建新的 owner，每次写入有独立 revision。页面列出当前账号的每份恢复副本，其他未打开的恢复稿不会阻止新建作品。

保存、放弃当前编辑和删除作品只清捕获的本页面、本作品恢复记录。恢复其他页面或旧版账号键中的稿件时，复制完整编辑内容到当前页面，来源保留并在界面说明。对来源副本的明确放弃只隐藏当时选择的 revision；原文不作跨页面物理删除，来源页随后写入的新版本仍可显示。旧版副本按完整原始内容匹配，不能仅比较时间戳。浏览器存储读取或写入失败会显示错误，候选与导出入口保留；隐藏来源版本不会自动释放正文占用，也没有自动清理未保存稿。

独立审查还发现候选修复中的 XM-028：另存失败后修改副本，再保存会误清含唯一未保存内容的原完整稿。实际复现后，正文或设定修改、离开编辑器和重新恢复都会撤销旧的副本清理关联，只修改内存关联，不删除原文；当前编辑器原样重试成功仍可清理已保存的本页面冗余副本。两条重试路径分别通过实际页面复测。

## 第二十轮：TXT 字节与 AI 预览保护

2026-10-08 的 User 体验确认两处缺陷：GBK 中文 TXT 被 `File.text()` 静默替换为乱码却提示导入成功；停止续写后删除目标章节，会同时清掉尚未插入的 AI 预览。现在按实际文件字节严格解码 UTF-8，不合法时明确提示另存为 UTF-8，已有作品和正文不变。支持 UTF-8 TXT/JSON（含 BOM），保留合法换行、空白、emoji 和字面替换字符；实际 1.5 MB 上限仍适用，不猜测其他编码。
