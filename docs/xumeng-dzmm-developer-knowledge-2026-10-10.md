# DZMM 官方技术规则与叙梦项目用途

这些规则来自 DZMM 官方 Gamefy 开发者文档和 Bot 接入指南，用于补充 AI小说文爱角色扮演技术群调研。它们不是群原始发言，也不能证明某个故障在群内出现过。对叙梦最有用的是付费生成的并发控制、结构化输出校验、存档确认、分支一致性和错误收口。

Gamefy 文档版本为 `50dd12a6ec4b`，正文注明核对日期为 2026-10-05，本次访问日期为 2026-10-10。[官方索引](https://www.dzmm.ai/gamefy/llms.txt)与[官方全文](https://www.dzmm.ai/gamefy/llms-full.txt)由 Workbench 帮助入口引用，各条下方给出单篇来源。Bot 内容来自官网发布的接入指南，未标注独立文档版本。

首次采集成功读取了文档正文并核对单篇地址；同日后续独立复查遇到 403。下文对应首次取得的版本，接口集成前应从官网帮助入口重新核对当时的契约，链接访问失败本身不能证明规则已变更。

**适用范围：**Gamefy 的 SDK 规则约束 DZMM 游戏卡运行环境。叙梦当前采用自己的 Next.js 和 Cloudflare 后端，调用契约、存储能力与运行环境不同。下文“官方规则”是源平台事实，“项目用途”是设计建议，不能把 Gamefy 的 `system` 限制、沙箱限制或配额数值直接套到叙梦现有接口。

## AI 生成与结果校验

### Gamefy 对话调用有独立契约

- **官方规则：**`dzmm.completions()` 只接收 `user` 和 `assistant` 消息，不接受 `system`。返回值为 `Promise<void>`，生成文本由回调提供。回调中的 `content` 是截至当前的完整文本，应覆盖旧内容。
- **典型踩坑：**照搬 OpenAI 兼容接口的参数；读取 `result.text`；用 `+=` 处理完整文本，造成回复重复。
- **项目用途：**若编辑器增加 Gamefy 导出或 SDK 适配，单独建立接口适配层，将角色规则转换成该接口接受的消息，并明确区分累计文本与增量文本。叙梦当前聊天后端是否接受 `system` 应由自己的契约决定。
- **来源：**[AI 对话](https://www.dzmm.ai/gamefy/docs/sdk/completions.md)。

### 超时与取消必须区分真实请求状态

- **官方规则：**安全调用 recipe 要求防止重复点击，并用递增请求标识阻止旧响应覆盖新界面。本地 deadline 只结束界面等待，不保证底层付费请求已取消；原请求结束前仍应保持付费请求锁。同一次用户动作不自动重试 AI。
- **典型踩坑：**界面超时后立即解除锁，允许用户启动第二个仍在计费的请求；切换会话后，旧响应写入新会话。
- **项目用途：**复查聊天、记忆补存和建议回复的生成状态：把“停止等待”“取消请求”“请求最终结束”分开，绑定账户、会话、源消息和请求标识。失败后提供明确操作入口，避免后台重试产生重复费用。
- **来源：**[AI 调用竞态与错误处理](https://www.dzmm.ai/gamefy/docs/recipes/completions-safe.md)。

### AI JSON 需要校验后才能改变业务状态

- **官方规则：**结构化输出 recipe 要求解析、字段校验和递归净化，拒绝原型敏感键。解析或校验失败后使用本地确定性降级结果，同一次动作不发送额外修复请求。
- **典型踩坑：**把提示词中的“必须输出 JSON”当成格式保证；解析后直接合并到状态，接受未知字段、越界数值或模型补造的事实。
- **项目用途：**复用现有记忆和世界状态校验思路：先验证版本、字段、范围和来源，再提交更新；校验失败保留原状态。剧情正文可以继续展示，结构化状态更新不能因正文存在就视为成功。
- **来源：**[结构化 JSON 输出](https://www.dzmm.ai/gamefy/docs/recipes/ai-json.md)。

### 模型目录与用户设置承担不同职责

- **官方规则：**Gamefy 的 `model: 'default'` 使用当前 Chat 的模型设置；自建选择器读取动态模型列表，展示用 `displayName`，调用用 `internalName`。目录中的 `defaultModel` 用于初始化选项，不代表玩家当前选择。
- **典型踩坑：**硬编码短模型名；把展示名传给接口；把平台推荐默认值误当成用户已经选择的模型。
- **项目用途：**叙梦模型菜单、实际调用模型和计费档位应共享稳定标识。目录刷新不能悄悄改变用户已选项；回退模型时应核对能力、价格与输出限制。
- **来源：**[动态模型选择](https://www.dzmm.ai/gamefy/docs/recipes/model-picker.md)。

### 能力检查不能替代余额和业务权限检查

- **官方规则：**`capabilities.get()` 返回宿主支持的静态能力，不返回余额、配额或模型目录。基础 KV 可用不代表批量、列举或原子创建可用；可选能力缺失时按不可用处理，不能根据设备或 dev/prod 推断。
- **典型踩坑：**看到 SDK 对象存在就调用高级方法；看到 `draw: true` 就认为编辑图片、下载图片也可用。
- **项目用途：**Gamefy 导出时按能力启用功能，并保留降级路径。叙梦自身新增多媒体或外部连接时，可分别建模“接口支持”“用户有权使用”“余额足够”，避免界面把三者混成一个开关。
- **来源：**[能力检查](https://www.dzmm.ai/gamefy/docs/sdk/capabilities.md)。

## 分支与存档

### 聊天消息标识不能兼任自造剧情节点标识

- **官方规则：**SDK 返回的 message ID 必须原样保存和回传，不解析、不拼接、不自行编造。只有 `chatStableIds === true` 才保证现代分支合同和长期稳定 ID；旧宿主仍支持基础调用，但不保证同一分支语义。稳定合同下，空 parent 续接当前叶子，显式 parent 才表示从指定节点分支。
- **典型踩坑：**用空 parent 创建新分支；裁剪 UUID；假设旧宿主始终返回 `insert().ids`；依赖未承诺的 `parent` 或 `children` 字段。
- **项目用途：**若接入平台聊天存档，业务剧情节点与外部消息 ID 分开保存。叙梦自己的分支、重生成和导入流程应显式保存分支归属，并让记忆与世界状态匹配对应消息前缀。
- **来源：**[聊天存档](https://www.dzmm.ai/gamefy/docs/sdk/chat.md)。

### 接受写入与确认落盘是两种状态

- **官方规则：**生产 Web Host 的普通 `kv.put()` 可能采用防抖，Promise 完成只表示写入已被接受。需要确认手动存档或付费结果时使用 `{ flush: true }` 并处理失败。`get()` 返回包装对象；`put(key, null)` 保存 JSON null，删除应调用 `delete()`。
- **典型踩坑：**普通 put 完成就显示“保存成功”；把 null 当删除；读取包装对象时漏取 `.value`。
- **项目用途：**叙梦继续区分本地变更、同步中和服务器确认。记忆补存只有在服务端确认且对应消息前缀仍有效时才能更新成功状态，不能只看生成完成或写入队列已接收。
- **来源：**[KV 存储](https://www.dzmm.ai/gamefy/docs/sdk/kv.md)。

### 多存档槽保存轻量且带版本的数据

- **官方规则：**每槽保存小 JSON，大资源只存 URL、asset ID 或轻量引用；结构带版本以便迁移。`batchGet` 与 `batchPut` 每批最多 10 项，完整请求和响应各不超过 5 MiB；同一批写入原子提交。远端与降级存储都失败时必须明确失败。
- **典型踩坑：**把 base64 图片连同每个存档重复保存；槽位字段分开写入后得到不一致组合；把未保存伪装为成功。
- **项目用途：**叙梦备份、会话导出和编辑器项目文件可分别保存状态、内容和资源引用，并保留 schema 版本。来源签名或媒体链接的可恢复性应单独处理，不能仅依赖“大 JSON 能导出”。
- **来源：**[多存档槽与 KV 扩展](https://www.dzmm.ai/gamefy/docs/recipes/save-slots.md)。

### 重置存档前必须停止旧写入

- **官方规则：**有进度的 Gamefy 游戏应接入 `save.onAction()`。重置和删除记录准备阶段先停 autosave，再清除全部自有存档 key；重置后更新内存状态。返回失败、异常或超时会阻止平台继续操作。
- **典型踩坑：**只删主存档而遗漏背包或标志；删完后旧 autosave 又写回；把 `prepareDeleteRecord` 当成游戏自己删除平台列表记录。
- **项目用途：**会话删除、导入覆盖和新开局应先隔离旧请求与旧写入，再清理关联记忆、世界日志和缓存。建议把同一会话拥有的数据集中列举，保证删除和备份采用同一边界。
- **来源：**[存档生命周期](https://www.dzmm.ai/gamefy/docs/sdk/save-actions.md)。

### 页面关闭不是唯一保存时机

- **官方规则：**官方 FAQ 建议在通关、选择分支等有意义的状态变化后立即保存，不能依赖 `beforeunload`。强制关标签页或切应用时，浏览器可能不给最后一次写入执行时间。
- **典型踩坑：**把退出事件当成自动存档的主要入口；移动端后台关闭后丢失整段进度。
- **项目用途：**叙梦消息完成、角色编辑和剧情状态更新可采用及时保存与明确同步状态。退出提示只能提醒未完成同步，不能替代过程中保存。
- **来源：**[常见问题](https://www.dzmm.ai/gamefy/docs/faq.md)。

## 运行环境与交付

### Gamefy 沙箱与普通网页有不同边界

- **官方规则：**Gamefy 游戏在没有 `allow-same-origin` 的 iframe 内运行，不能访问宿主页面、Cookie、localStorage、sessionStorage 或 IndexedDB；平台能力通过 `dzmm.*` 调用。平台发布物是静态前端，服务端逻辑使用平台函数。
- **典型踩坑：**把同源本地预览成功当成沙箱兼容；使用 `parent.document`；把 Express 或 Flask 服务当成可发布的游戏入口。
- **项目用途：**如果编辑器生成 Gamefy 作品，需要提供沙箱预览与独立 SDK 适配。叙梦自己的站点仍可使用其同源存储，不能为模仿源平台而删除当前正常能力。
- **来源：**[游戏运行环境](https://www.dzmm.ai/gamefy/docs/runtime.md)。

### 启动进度必须有终止状态

- **官方规则：**显式调用 `loading.progress()` 后，宿主等待游戏主动发送 `ready()` 或 `error()`，普通 load 事件不会提前结束这个流程。`ready()` 表示首个可交互画面已经就绪。
- **典型踩坑：**报告开始加载后漏报完成；把大图片或 BGM 下载放进首屏，却没有失败出口，形成无限 loading。
- **项目用途：**编辑器预览和故事首屏可分开显示资源准备、界面就绪与生成进度。每个启动分支都需要到达成功或失败状态，不能让可恢复媒体失败阻塞整个剧情入口。
- **来源：**[启动加载状态](https://www.dzmm.ai/gamefy/docs/sdk/loading.md)。

### 音频播放需要处理浏览器手势限制

- **官方规则：**Gamefy 音频使用 `dzmm.audio.*`，由 SDK 处理平台音量、首次手势解锁和后台暂停。`play()` 通过 `{ ok, reason }` 返回结果而非抛异常；`pending_gesture` 表示等待用户手势。
- **典型踩坑：**直接 `new Audio()` 后认为调用即播放；把移动端未解锁音频当成加载失败；游戏音量绕过平台设置。
- **项目用途：**互动视频与叙事编辑器可把首次声音解锁放在开始按钮，并区分资源不存在、浏览器等待手势和用户静音。Gamefy 导出时通过平台音频接口播放。
- **来源：**[音频播放](https://www.dzmm.ai/gamefy/docs/sdk/audio.md)。

### 保存代码 发布版本与上架审核分别处理

- **官方规则：**保存更新工作区或 Git 版本；发布更新线上代码；上架提交审核并改变公开状态。静态版本切换是原子的，但工坊函数上传失败可能只给警告并保留旧函数。未上架的静态文件仍可能凭完整地址被读取。
- **典型踩坑：**发布成功就认为玩家可以访问；忽略函数警告，形成新前端调用旧函数；把未上架当成静态内容保密。
- **项目用途：**叙梦私人草稿、投稿快照、批准版本和公开素材需要继续分开。编辑器若增加 Gamefy 发布器，应展示静态发布、函数部署、审核状态各自的结果，并在验证通过后才宣称整体成功。
- **来源：**[发布与上架](https://www.dzmm.ai/gamefy/docs/publishing.md)。

### 本地部署需要保留版本冲突保护

- **官方规则：**`gamefy deploy` 会检查线上 revision，冲突时报 `revision_conflict`。CLI 发布本地文件，不会自动同步回工坊容器；工坊之后继续编辑需要从线上恢复。CLI 对函数上传失败的处理比工坊严格。
- **典型踩坑：**把 CLI 发布后的工坊旧文件继续发布；遇到冲突直接强制覆盖而丢掉另一端更新。
- **项目用途：**编辑器未来连接云端项目时保存基准版本，拉取、合并和部署分开。叙梦的账户同步冲突也应保留可恢复数据，避免只靠“最后写入覆盖”处理。
- **来源：**[本地开发 CLI](https://www.dzmm.ai/gamefy/docs/connected-dev.md)与[发布与上架](https://www.dzmm.ai/gamefy/docs/publishing.md)。

## 服务端边界与故障诊断

### 服务端提示词不能替代确定性权限规则

- **官方规则：**服务端函数可避免提示词源码直接下发，但模型仍可能复述服务端指令。密钥、密码和安全关键规则不能放进 prompt；权限判断和防作弊由确定性服务端代码执行。
- **典型踩坑：**把“模型不得泄露”当成秘密保护；让模型决定用户是否有权读取数据或领取奖励。
- **项目用途：**叙梦账户归属、计费、发布权限和数据访问继续由后端校验。模型生成剧情或提议状态变化，后端负责判断哪些变化能被接受。
- **来源：**[服务端函数是什么及何时使用](https://www.dzmm.ai/gamefy/docs/serverless.md)。

### 玩家私有数据与全游戏共享数据分别建模

- **官方规则：**浏览器 KV 是当前 chat 与玩家的范围；服务端 `ctx.kv` 是 game 与玩家范围；跨玩家共享使用 `ctx.kv.global`。开发数据与生产数据隔离，global KV 没有事务或 CAS。
- **典型踩坑：**用玩家私有 KV 做排行榜；开发预览读不到生产数据就判断存储坏了；用非事务读改写计算严格排名或奖励。
- **项目用途：**叙梦私人会话、公共角色与社区账本应采用不同权限和数据边界。需要精确结算的功能使用当前后端事务与唯一约束，不能照搬展示型共享 KV。
- **来源：**[服务端 ctx API](https://www.dzmm.ai/gamefy/docs/serverless/ctx.md)。

### 错误码驱动恢复流程

- **官方规则：**普通 SDK 常用 `DzmmError`，函数调用使用 `RPCError`；公共处理读取稳定 `error.code`，不能只按异常类或多语言 message 判断。自动 toast 不会吞掉异常，仍需 catch。`retryable` 只表示以后可能恢复，不代表本次付费动作应该重复调用。
- **典型踩坑：**只显示报错而没有解除 loading；网络错误反复自动重试；余额不足继续请求；同一错误同时触发平台和业务重复提示。
- **项目用途：**聊天与记忆补存采用统一错误分类：登录失效、余额不足、限流、取消、网络和格式失败对应不同操作。所有失败路径恢复可操作界面，并保留可诊断的请求状态。
- **来源：**[错误处理大全](https://www.dzmm.ai/gamefy/docs/errors.md)。

### 运行日志不能充当保存或支付凭证

- **官方规则：**`dzmm.log.*` 面向作者排错，发送错误会被内部吞掉，不保证保存。日志有额度和保留期限；稳定 code 配合少量上下文有助于聚合同类问题。
- **典型踩坑：**日志出现“成功”就认为业务提交已完成；逐帧刷日志；记录 token、完整私人对话或签名资源 URL。
- **项目用途：**叙梦可以记录生成开始、超时、校验失败、记忆提交失败等阶段及稳定错误码，关联不含秘密的请求标识。计费结果和数据提交仍以业务表状态与服务器回执确认。
- **来源：**[游戏日志](https://www.dzmm.ai/gamefy/docs/sdk/log.md)。

## Bot 接入资料

Bot 指南描述的是 DZMM 平台群聊 Bot，与直接读取 Telegram 目标群历史不是同一接口。其内容可供以后明确授权的集成参考，不能据此取得目标群历史，也不表示本次已创建 Bot 或发送消息。

### Bot 接收回调前校验密钥和群权限

- **官方规则：**Webhook 必须是公网 HTTPS，平台拒绝 localhost、内网地址和非 HTTPS。平台用 `X-Telegram-Bot-Api-Secret-Token` 传递 Webhook Secret；服务先校验再处理。Bot 必须加入目标平台群，发送到未加入的群会返回 403。
- **典型踩坑：**把 `X-Bot-Secret` 当成正确 header；只创建 Bot 却没有加入群；使用本机地址测试公网回调。
- **项目用途：**若将来获得群消息接入授权，可用独立接收服务校验回调身份，按群范围处理数据。当前调研的群历史采集仍依赖已授权的 Telegram 客户端读取或用户导出。
- **来源：**[Bot 接入指南](https://www.dzmm.ai/studio/bots/docs/)，[官网发布的指南正文资源](https://www.dzmm.ai/assets/DQCRp9VJ2.js)。

### Bot 的接口兼容范围需要逐项确认

- **官方规则：**指南提供 `send-message` 及 Telegram 风格的 `sendMessage`、`sendPhoto` 路径。图片只接受 URL，不支持 multipart 上传；置顶要求 Bot 已在群内且目标消息属于同一群。
- **典型踩坑：**把“Telegram 兼容”理解为 Telegram Bot API 全部方法可用；把 Telegram 群 ID 当成 DZMM 平台群 ID。
- **项目用途：**外部服务适配应逐项记录已支持方法和 ID 范围。若以后增加技术知识机器人，只围绕明确授权的群和接口设计，不能从有限兼容能力推断历史读取能力。

## 叙梦建议先复查的三条链路

1. **记忆补存：**将生成完成、JSON 校验、消息前缀匹配、服务端提交和成功提示分别确认；每个失败阶段都能结束等待并保留原有效记忆。依据是上面的调用锁、结构化校验和落盘确认规则，不能据此断言现有实现有故障。
2. **长对话与分支：**用明确的业务分支和来源范围约束记忆及世界状态，阻止迟到请求覆盖已切换会话。这是通用设计迁移；官方 Gamefy 文档没有证明叙梦世界书被忽略或长上下文变慢的具体原因。
3. **错误与计费：**把本地超时和真实请求结束分开，复查付费动作去重、服务端回执和界面恢复。后续应结合群原始案例及本站日志验证，而不是仅凭官方 FAQ 标注修复完成。
