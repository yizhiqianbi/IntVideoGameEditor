## Inferred

- The normal chat generation request is a Rails/Turbo form POST to `/messages`; server-side response is delivered as HTML/Turbo Stream and may update message IDs, loader, sidebar, paywall, and token UI. Exact model/provider, prompt assembly, memory retrieval, and charge transaction are not present in the browser code.
- Dynamic message form fields indicate profile and conversation IDs are server-rendered; an empty conversation ID on guest role page is consistent with no authenticated conversation.
- `data-video-token-price="12"`, token-price datasets, and balance-after calculations expose client display/eligibility checks only; debit authority remains server-side.
- Memory lifecycle is primarily server-rendered/Turbo-driven: JS exposes badge visit marking and memory dialog UI, but no public memory CRUD/generation endpoint or payload.
- `Pp` never calls the request helper itself; native Turbo form submission would own the server-injected action, method, encoding, body fields and response target. Any exact `data-action` wiring for the absent guest form is a reconstruction candidate, not an observation.
- Audio call persistence is separate from text `/messages`; the addon stores role-tagged transcripts and `assistant_token`, then marks completion. `premium_required` from token check redirects to `/subscriptions`.
