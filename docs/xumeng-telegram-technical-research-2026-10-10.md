# AI小说技术群问题与叙梦改进建议

调研日期：2026-10-10。对象是 [AI小说文爱角色扮演技术群](https://t.me/ai_xiaoshuo)。对叙梦最有用的内容是长对话事实记忆、作者设定是否真正进入上下文、存档能否恢复，以及生成失败时的状态与费用解释。建议先建立真实故障回归集，再扩充整书记忆和角色卡兼容性。

**这是首批问题归纳，不是全群历史的全量调查。** 本机 Telegram 可读取实际群消息；本轮读取 DZMM 反馈话题的 17 组关键词首屏结果，并在全群检索 7 组关键词。单个 DZMM 话题当时显示约 18.4 万条消息，尚未取得历史导出、逐条消息编号、完整回复链和图片附件正文。因此下面不能用于统计问题发生率，也不能把群友的判断当成已验证根因。

## 来源与复核方法

材料分为三个层次：群消息只证明用户表达过某种现象；关联官网文档说明该平台的接口规则；项目源码说明叙梦当前的能力与边界。每项的处理建议是依据前两者、结合第三者作出的工程判断，没有在本轮执行真实模型生成、付款或故障复现。

群与服务的关联可由 [DZMM 官网](https://www.dzmm.ai/)以及 [酒馆AI机器人简介](https://t.me/jiuguanzbot)核对，两处均指向目标群。这里的“酒馆AI”是群关联的机器人服务；[SillyTavern](https://docs.sillytavern.app/)作为另一套角色聊天软件，仅用于机制比较。

复核群观察时，打开目标群，搜索下表关键词，再按客户端显示的日期定位。搜索摘要被截断的部分没有补写，未获取的消息编号留空。结构化记录见 [群问题记录](../output/research/ai-xiaoshuo-2026-10-10/group-observations.json)。记录只保留技术现象的原创概括，不保存发言者姓名、支付明细或私人创作正文。

DZMM 反馈话题检索词为：记忆、世界书、存档、复读、报错、登录、充值、画图、提示词、模型、加载、浏览器、游戏、导入、丢、扣、小说。全群检索词为：世界书、API、语音、代码、Gamefy、角色卡、教程。检索首屏偏向近期内容，不能代替按时间遍历。

## 官方资料中可以直接沉淀的知识

[DZMM 官方技术规则与叙梦项目用途](./xumeng-dzmm-developer-knowledge-2026-10-10.md)单独整理了 21 条可核对规则，涵盖模型调用、JSON、分支、KV、存档、沙箱、声音、发布和 Bot 接入。它们补充群问题，不能作为“群里出现过这些故障”的依据。

其中最容易造成实际错误的四项是：Gamefy 回调给的是累计全文，不能重复追加；本地超时不等于底层付费请求取消；普通 KV 写入被接受不等于已经落盘；保存、发布和上架是三个独立动作。具体接口约束以[对话契约](https://www.dzmm.ai/gamefy/docs/sdk/completions.md)、[安全调用](https://www.dzmm.ai/gamefy/docs/recipes/completions-safe.md)、[KV 文档](https://www.dzmm.ai/gamefy/docs/sdk/kv.md)和[发布文档](https://www.dzmm.ai/gamefy/docs/publishing.md)为准。

这些约束属于源平台。叙梦当前的游戏工作台只是私人单文件 HTML 编辑、试玩与源码备份，没有 Gamefy SDK、付费 AI 桥或玩家进度存档；不能照搬其方法名、配额和角色限制。

## 原理校验与可复现条件

世界书插入和模型遵循应分别测量。SillyTavern 的条目还受扫描、条件和预算影响，即使插入也不保证被模型遵循；这只能作为对照机制，不能证明 DZMM 的实现相同。[World Info 官方文档](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)

长输入可能增加处理负担，但输出长度和串行调用也影响时延。记录上下文构建、首 token、完整输出和保存时间，用同模型、同参数和固定输出上限比较；本轮没有证据证明群里的延迟由上下文、数据库或某个供应商单独造成。[时延优化](https://developers.openai.com/api/docs/guides/latency-optimization)

模型升级需固定可识别版本并保留评估集；结构化 JSON 格式通过也不能证明事实正确。摘要应分别测遗漏、编造、冲突与来源覆盖，不以字段齐全代替语义验收。[提示词与评估](https://developers.openai.com/api/docs/guides/prompt-engineering)、[结构化输出](https://developers.openai.com/api/docs/guides/structured-outputs)

费用比较应包括稳定前缀、缓存、摘要和失败请求；供应商的缓存条件需要逐型号核对。页面收到文本增量也不等于生成和保存均成功，要单独处理完成与错误生命周期。[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)、[Streaming responses](https://developers.openai.com/api/docs/guides/streaming-responses)

D1 的批事务不能覆盖模型与 R2；R2 桶直读强一致，经缓存域名读取仍可能旧内容或缓存 404。保存后看不到新内容时先对比业务版本、桶直读和域名响应，再判断写入是否失败。[D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/)、[R2 一致性](https://developers.cloudflare.com/r2/reference/consistency/)

## 全量历史需要补齐的数据

完成“所有技术相关问题”的调查，需要目标群可访问历史的 JSON 或 HTML 导出。Telegram 官方提供单个聊天的 `… → Export chat history`，可选择 JSON 或 HTML；优先 JSON、完整日期范围及文字，先不用下载所有媒体。[Telegram 官方导出说明](https://telegram.org/blog/export-and-more)

取得数据后应记录实际起止日期、消息总量、导出遗漏和分话题覆盖，再按消息与回复编号复原问题链，合并重复问题，分别标记无答案、群友建议、维护者解释和已有复现。频率统计须明确分母、独立发言者和事件去重，不能用关键词命中数当故障次数。

每条最终知识至少保存来源链接、发生条件、现象、答案身份、处理办法、适用版本、与叙梦模块的映射和验收场景。图片中的报错、已删消息及未导出的旧历史应列为覆盖缺口。当前这批 34 类问题和 21 条官方知识可继续增补，但不应重命名为全量结论。
